# 持续监控第二阶段：长期分析与诊断

状态：P2-A/B/C 已实现并部署；2026-09-09 已补充概览、节点详情、事件时间线和监控设置的[实机截图与读图说明](../monitoring.md#live-screenshots)。设计基线 `04d01bb`；实现日期：2026-09-09。截图中的评分仍为暂定分，不代表完整 24 小时／7 天覆盖或长连接验证。

实现说明：不可变方案修订承担成员关系历史；原始迁移采用可恢复水位，小时聚合使用紧凑时隙数组直接保留精确延迟，不另存冗余直方图。浏览器导出使用JSON/Base64封装以兼容默认下载器。当前行为以[使用说明](../monitoring.md)为准，以下保留设计与验收依据。

## 1. 本阶段要交付什么

让用户能回答三个问题：过去一周哪个节点持续可靠；一次中断是个别节点还是一组候选共同异常；切换前后发生了什么。

交付范围：

1. 1 小时观察、24 小时与 7 天排名，明确区分当前健康和历史成绩。
2. 小时聚合、保留策略和存储占用，支持长期运行。
3. 调整候选列表时，未变化节点继续积累历史；能查看方案版本与历史节点。
4. Provider 相关异常提示、统一故障时间线和可导出的诊断包。

不包含：WebSocket 保活、真实模型请求、客户端日志自动采集、分布式部署或改变自动切换的择优规则。这些属于后续验证层或独立需求。

**自动切换仍固定使用近 24 小时基准成功率，再按 P95 排序。页面切到 7 天视图不会改变自动切换策略。** 现有新鲜度、切换前复测、2 分钟冷却、持久化审计和未知结果阻断继续生效。

## 2. 从现有代码确认的限制

| 现有行为 | 第二阶段的处理 |
|---|---|
| `metrics()` 固定取 24 小时 | 提取公共窗口计算，增加 7 天；1 小时用于观察，不强行生成长期分 |
| 修改节点集合会生成新的 plan ID | 将观测序列与方案成员关系分开，保留未变化节点的连续历史 |
| `monitor_plans` 仅保存每个 Controller 的当前 JSON | 保存不可变方案修订，避免历史样本失去模板、成员和采样时间基准 |
| 保留 7 天原始 JSON，按小时删除 | 先生成并校验聚合，再按容量与保留策略清理 |
| 当前页面只展示最近 60 条基准记录与 100 条事件 | 提供有时间范围和游标的趋势、事件与历史方案 API |
| 自动切换调用完整 Overview | 提供轻量、固定 24h 的决策快照，避免图表查询拖慢故障处理 |

参考：[监控存储](../../internal/history/monitor.go)、[评分](../../internal/monitor/metrics.go)、[方案保存](../../internal/monitor/manager.go)、[自动切换](../../internal/monitor/failover.go)、[现行使用说明](../monitoring.md)。

## 3. 页面设计

保持现有导航与主要操作，在持续监控页内增加三个视图：

### 总览

- 当前节点、即时健康、最近观测与故障自动切换开关仍放在顶部。
- 时间范围：`最近 1 小时`、`最近 24 小时`、`最近 7 天`。
- 1 小时显示成功率、P95、观测失败段和时间轴；24h/7d 显示长期 HTTPS 健康分。
- 排名表显示当前状态、窗口分数、成功率、有效/参考时隙、实际观测跨度、P95、观测失败段和估算不可用时长。
- 当前不可用或数据过期的节点单独分区。数据不足节点标记“积累中”或“暂定”，不混入正式排名。
- 分数可展开到分项及分子/分母；自动切换旁明确显示“依据：24h 成功率”，避免与浏览窗口混淆。

### 节点详情

- 上层健康时间轴：成功、失败、未知、未纳入监控；缺测保留空档，不连成健康区间。
- 下层延迟趋势：小时 P50/P95，仅基于成功的基准样本；未知区间断线显示。
- 叠加暂停、恢复、方案变更和手动/自动切换标记，点击标记查看审计状态。
- 保留当前列表之外的历史节点，显示最后监控时间和测量定义版本。
- 更换探测模板或不可识别的身份变化，用明确分界展示，不直接合并成一个排名。

### 诊断与存储

- 显示“所监控候选”的 Provider 状态、观测数量、共同异常区间与对照情况。
- 统一时间线包含确认故障、恢复、Controller 不可达、漏测、切换及未知结果。
- 选择时间范围后导出诊断摘要与明细。
- 显示原始样本/聚合/事件数量、整个数据库与 WAL 的实际大小、下一次清理、保留策略和聚合进度。

## 4. 观测序列与方案版本

引入 `observation_series`。身份由 Controller、节点身份、Profile 探测定义、传输证据级别和采样规则版本确定，不由节点在列表中的位置决定。

- 现有节点沿用自己的采样锚点/相位；添加新节点不会重新排列所有节点的执行时间。
- 新增、移除、排序或暂停是成员关系/方案修订，不清空现有序列。
- 移除后重新加入同一可识别节点、相同测量定义，可继续该序列，中间未监控区间保持未知。
- Provider、协议或探测定义变化产生新序列。只有名字相同不能证明出口相同，仍保留身份识别限制。
- 暂停、自动切换开关变化不重置历史，也不改变观测定义。

建议增量表结构：

| 表 | 内容 |
|---|---|
| `monitor_plan_revisions` | 不可变的方案、成员、模板哈希、采样规则、开关和时间快照 |
| `monitor_series` | 节点身份、模板/算法版本、首个观测时间、固定采样锚点与周期 |
| `monitor_memberships` | 方案修订与序列的加入、移除、暂停、恢复区间 |
| `monitor_hourly` | 每个序列的小时统计、时隙明细、延迟分布、聚合版本与输入水位 |
| `monitor_aggregation_state` | 回填进度、已完成区间、待重算区间及错误状态 |
| `monitor_correlations` | Provider 共同异常事件、关联节点集合、证据时间范围 |

样本补充 `series_id`、`scheduled_at`、`reason_code` 和数据版本；实际完成时间继续保留。原始失败不可被后续成功重试覆盖。

## 5. P1 数据迁移

采用增量迁移，不在首次启动时删除 P1 表或清空当前方案。

1. 保存当前方案的不可变修订，保留 plan ID、revision、开始时间、成员、监控及自动切换偏好。
2. 对当前方案的节点建立序列。根据其原始创建时间、成员位置和 120 秒周期，恢复计划采样时间；不能用请求完成时间替代计划时间。
3. 给可可靠关联的旧样本补齐序列与采样定义，保留成功/失败/未知原值。旧的通用错误原因标记为 `legacy_unclassified`，不靠字符串猜测具体网络根因。
4. 后台分批回填聚合，读路径可暂时使用原始记录；聚合未完成不能清理其源数据。
5. 恢复原有监控偏好，完成新鲜的成员/状态核实后才允许自动切换。迁移本身不改生产节点。

**明确的历史限制：**P1 曾经被替换的旧方案可能只剩 sample 的 plan ID，而没有完整方案 JSON。不能把这些样本强行套入当前模板或猜测其采样锚点。此类数据作为“缺少方案元数据的历史记录”保留/导出，不进入正式排名。P2 保存修订后不再产生这种缺口。

验收必须覆盖“升级已有六节点监控”“新增一个候选后原节点数据连续”“重排列表不改变序列”“失败的迁移可恢复”。

## 6. 小时聚合：必须保留哪些信息

每个两分钟基准序列在一个完整 UTC 小时最多有 30 个时隙。聚合不仅保存平均值，还保留这些时隙的结果与成功延迟，以支持精确的窗口裁切。

- 统计项：参考时隙、有效、成功、失败、未知、缺测分类。
- 每时隙：计划位置、结果类型、成功延迟；保留失败边界，以合并跨小时的观测失败段。
- 全小时优化：稀疏的整数延迟频数表 `[delay_ms, count]`，最多约 30 个不同值，便于合并精确 P50/P95。
- 当前节点检查、手动复测、确认和切换前验证分别记数量/事件，不混入基准统计。

**不能平均各小时 P95，也不能简单把每小时失败段数相加。** 跨小时连续失败要合并，未知/缺测打断可确认的连续性；“观测失败段”与状态机确认故障事件分别统计。

滚动 24h/7d 查询：完整小时可使用聚合，首尾不足一小时按保存的时隙明细裁切；正在形成的小时使用原始记录。每个时隙只能取一个数据来源，禁止原始与聚合重叠累加。

封存延迟建议两分钟；若有合法迟到写入则标记该小时重算，而不是忽略新记录。聚合按确定的输入水位原子 upsert，重复执行和中途重启不能增加计数。首个观测前、暂停或移除期间的缺口在查询时生成，不为每个空小时都写一行。

## 7. 评分与充分程度

24h 与 7d 继续使用已有 `70A + 20C + 10L`，冻结为明确版本。P2 扩展时间窗口和数据来源，不借机改权重或自动切换排序。

- A：窗口内有效基准样本的成功比例。
- C：延用有效观测时长归一化后的基准失败段惩罚。
- L：成功基准样本的 P95 项；全失败总分为零。
- 少于 100 个有效样本为积累中；完整跨过对应窗口且覆盖率至少 80% 才是数据充足。
- 7 天只有几小时数据时，必须同时显示“已观察 X 小时 / 7 天”和暂定状态；不能只显示一个高分与 100% 覆盖率。
- 覆盖率分母仍从该序列首次纳入与窗口起点的较晚者计算，之后暂停、漏测和移除空档不消失。正式榜另要求完整窗口跨度。
- 当前观测过期影响即时状态和切换资格，不抹除可信的历史成绩。
- 不同模板、证据级别和不兼容算法版本分别排名，不能把 HTTPS 探测分冒充 WebSocket 稳定分。

聚合与原始参考实现的成功率、计数、P95、失败段及分数应一致；不能用“看起来接近”代替回归验证。

## 8. Provider 相关异常

利用已有采样做相关提示，不默认增加外部请求或把未选择节点加入监控。

建议初始触发条件：同 Provider 至少三个有效观测候选，最近四分钟内至少 80% 确认不可用，连续两个评估轮次出现；阈值在试运行后校准。

- 另一 Provider 有同服务成功样本：提示“该 Provider 所监控候选疑似共同异常”。
- 只监控了一个 Provider，或所有 Provider 同时异常：提示“缺少对照，暂不能区分共同上游与本地环境”。
- Controller 不可达：优先展示控制器异常，不能生成一组“节点服务器宕机”的结论。
- 事件显示 `失败节点数 / 可比较节点数`、各节点最近观测时间及重叠时段；不外推整个订阅都坏了。
- 每个异常区间只开一条关联事件，更新成员与持续时间，恢复后关闭。

相关性不改变原始样本，不自动免除失败分，也不强制自动切换到某个 Provider。当前仍按用户要求的节点成功率择优。

## 9. 保留与容量

初始建议：原始样本 7 天，小时聚合与诊断事件 90 天。切换审计继续沿用独立保留规则；未确认操作不能随监控清理删除。

首版容量约束建议同时采用原始样本行数和聚合行数上限，例如 100,000 / 20,000，作为可配置初值。记录量不足时按时间保留，上限先到则优先清理已成功聚合的最旧明细，并显示明细实际可用起点。不能在聚合失败时为满足配额删掉唯一证据。

监控与扫描共享 SQLite：界面分别显示监控记录量及整个 DB/WAL 文件大小，不把估算的监控字节数称为精确物理占用。磁盘空间不足时暂停新增监控写入并告警；具体磁盘阈值在路由器试运行测量后设定。

聚合/清理采用可恢复的小批事务，不持有监控决策锁，不高频 VACUUM。保持扫描、探测和自动切换优先；后台批次有截止时间，过载后推迟聚合。

## 10. API 与一致性

沿用认证、CIDR 与写操作 revision；GET 不改变配置。建议：

| 接口 | 用途 |
|---|---|
| GET `/monitor?window=24h` | 当前状态和所选窗口排名；支持 1h/24h/7d |
| GET `/monitor/nodes/{series_id}/timeline` | 有界时间轴、趋势及事件 |
| GET `/monitor/revisions` | 历史方案修订和可用测量版本 |
| GET `/monitor/incidents` | 节点、环境、Provider 与切换事件，游标分页 |
| GET `/monitor/storage` | 记录量、聚合水位、保留状态、DB/WAL |
| PUT `/monitor/retention` | 修改保留策略，带 revision |
| POST `/monitor/diagnostics` | 显式生成诊断包，不上传外部服务 |

概览返回数据水位/版本和 freshness，避免旧响应覆盖新状态。重型历史读取在监控锁外执行；最新状态和统计需要同一逻辑快照。

自动切换使用内部轻量的固定 24h 决策快照，不调用用户选择的 7d 图表接口，不等待长时间历史回填。首次切换前仍会重新验证候选、组成员和当前选择。

## 11. 诊断导出

默认导出指定故障时间前后的小窗口，可调但有记录数与文件大小上限。

- `summary.md`：症状、时间线、候选成绩、失败/恢复与切换结论，区分事实和推测。
- `samples.csv`：基准与附加检查分类、结果、延迟、规范化原因。
- `incidents.json`、`switches.json`：关联事件和审计状态。
- `manifest.json`：时间范围、UTC与展示时区、算法/模板版本、聚合水位、缺测及删减说明。

默认使用包内一致的节点/Provider 别名，不导出 Controller secret、token、订阅地址、私有探测 URL、全网连接列表或聊天内容。若需要真实节点名称，用户在导出界面明确选择。CSV 单元格处理公式前缀，文件名和生成路径固定在受控目录；下载后按短期策略清理临时包。

## 12. 交付顺序与验收

### P2-A：历史连续性与聚合底座（优先实施）

不可变方案修订、观测序列、P1 当前数据迁移、可恢复小时聚合和清理顺序。完成后原节点不再因列表调整重新积累，聚合重跑不重复计数。自动切换与现有开关行为回归通过。

### P2-B：7 天榜与历史详情

公共窗口计算、1h/24h/7d 视图、跨度与充分程度、健康时间轴、跨小时失败与准确 P95。浏览器验证桌面/手机、明暗主题、旧响应、分页、零样本、全失败、缺测与历史版本分界。

### P2-C：诊断闭环

Provider 相关提示、存储策略页面、统一故障时间线和诊断包。验证单 Provider 无对照、广泛环境异常、恢复去重、导出隐私与 CSV 安全。

关键测试集：

- 随机生成七天成功/失败/缺测序列，对比原始与聚合的全部指标；覆盖小时边界、部分小时、午夜和时钟回退。
- 故障跨小时只算一个观测连续段；中间缺测不虚构连续可见证据。
- 更改候选顺序、新增/移除/重新加入、模板变化以及旧方案缺元数据。
- 聚合事务失败、重启、迟到样本、清理与聚合并发、磁盘不足。
- UI 切换到7天时，自动切换仍选中24h成功率最高且通过复测的健康候选。
- 大量图表读取或聚合时，自动切换审计、人工操作优先级与关闭开关仍正常。

性能验收目标需实测：六节点90天聚合数据下概览响应 P95 不超过500ms；单个聚合写事务尽量控制在50ms内；后台处理不增加探测预算且不导致持续漏测。以真实目标设备测量为准，不把交叉构建当作运行证明。

部署采用升级前备份、迁移状态可见、失败可恢复。先观察24小时的负载/写入/覆盖率，七天后再判断长期排名效果；这不阻止用确定性模拟数据提前验收算法与页面。

## 13. 本轮设计的明确决策

优先做数据连续性和聚合，再做7天页面，最后做相关提示和导出。暂不改变评分权重、自动切换窗口、候选范围或增加长连接流量。当前实现已部署，使用入口及运行快照见[持续监控说明](../monitoring.md)。以上设计与性能验收目标保留，截图不能替代完整窗口或设备负载验收。
