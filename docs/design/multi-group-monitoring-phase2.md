# 多策略组监控：第 2 阶段

本阶段在稳定任务 ID、独立配置和旧数据迁移的基础上，接入多个策略组的后台运行、统一调度、共享预算和按任务限定的操作与历史接口。前端多组导航、诊断导出和设备隔离验收现已在[第 3 阶段](multi-group-monitoring-phase3.md)完成，下文关于前端尚未接入的描述保留为本阶段的交付边界。

## 运行行为

- 保存任务时允许 `enabled: true`，所有已保存的任务都会接入同一个 Controller 的调度器。各任务按自己的 `enabled` 状态采样，暂停任务仍保留配置和历史。
- 启动时恢复全部任务，包括各自的候选、状态、已执行采样时隙和启停偏好；第 1 阶段保存为暂停的任务不会因升级自动启用。
- 每个任务独立维护当前选择、Controller/成员核实结果、健康状态、手动复测队列、配置取消句柄及切换状态。
- 按策略组轮转分配最多 **2 个后台执行槽位**，同一任务不会重叠执行。某组响应较慢时另一个槽位可服务其他组；每轮设置 45 秒取消期限，底层 Controller 调用保留自己的超时，已进入切换的独立回读按原有期限收尾。
- 到期任务每秒最多获得一次执行机会；完成后释放槽位给下一组。错过采样窗口不积压补跑，预算不足、扫描占用和缺测继续区别于节点失败。
- 所有任务只共享一个数据库维护循环和一个重历史查询槽位。概览缓存归属各任务，避免相同观察窗口和版本号导致串组。
- 保存或暂停某任务只取消该任务的在途探测；取消产生的迟到结果不会入库，正常取消不视为数据库故障。停止服务会取消全部任务，并等待后台退出，调用方等待时间受其 context 限制。

第 1 阶段表中的 `runtime` 标记继续作为旧单任务视图的兼容定位信息保留；它不再限制哪些任务可以调度。任务接口返回的 `scheduled` 由当前运行时注册状态决定。

## 请求预算与运行容量

每个任务的名义预算仍为 `max(12, 已选节点数 × 模板探测目标数 × 2)` 次/滚动分钟。统一预算为正在参与预算分配的任务名义预算之和，最高 **360 次/滚动分钟**。

- 总量未达到 360 时，各任务受自身名义预算及共享总量双重限制。
- 总量超过 360 时，按各任务名义预算比例分配额度，整数向下取整，每任务至少保留一个尝试机会；共享总量始终不能超过 360。过载可能造成缺测，不承诺任意数量任务都能满足原采样频率。
- 基准、当前节点检查、确认、复测和切换前验证都消耗同一组共享额度。
- 保存、暂停、继续任务不会清空已消耗的滚动额度；缩小监控规模后也可能需要等待已消耗额度过期。额度记录为进程内状态。
- 组失效或模板定义变更时，该任务暂停探测并退出预算分配，其他组仍可运行；Controller 整体不可达会使相关任务分别进入环境异常。
- 仍与手动扫描共用底层探测槽位。后台不会排在饱和的扫描之后补跑，也不会把槽位竞争归因为节点失败。

`GET /api/v1/monitor/scheduler` 返回 `workers`、`running_workers`、`max_requests_per_minute`、`requests_per_minute`、`requests_used` 和 `suspended`，用于查看后台约束和当前滚动请求量。此接口属于 Controller 范围。

存储数量上限保持原值，新增任务会更快消耗原始记录与小时聚合容量。本阶段没有扩大保留配额，也没有以源码或模拟测试替代路由器压力测试。

## 按任务操作与读取

继续使用第 1 阶段的任务创建、读取和 PUT 更新接口。新增路径均以 `/api/v1/monitor/tasks/{task_id}` 为前缀：

| 方法与后缀 | 行为 |
| --- | --- |
| `GET /overview?window=24h` | 此任务的概览；支持 `1h`、`24h`、`7d` |
| `POST /retest` | 传入 `revision`、`node_id`，只复测此任务候选 |
| `PUT /failover` | 传入 `revision`、布尔值 `enabled`，修改此任务自动切换偏好 |
| `GET /series` | 只列出此任务当前及历史修订所关联的观测序列 |
| `GET /nodes/{series_id}/timeline` | 查询属于此任务的历史序列，沿用观察窗口与时间范围参数 |
| `GET /incidents` | 查询此任务的修订、节点、环境、Provider 和切换事件，沿用时间范围及分页参数 |
| `GET /correlations` | 只读取此任务的 Provider 共同异常 |

任务间的事件游标不能混用。相同策略组名称在另一个 Controller 上产生的切换不会进入此任务的事件列表。自动切换仍通过原有 `monitor:{plan_id}` 审计来源与任务修订关联。

多任务状态下，未指定任务的旧监控接口继续返回 409。`catalog`、`retention`、`storage`、`scheduler` 保持 Controller 范围。单任务的原有前端与接口继续可用；前端多组切换尚未实现。任务诊断包下载接口留待后续界面阶段，底层导出查询已支持任务范围，无法归属的旧记录不能被标注为某个任务的历史。

## 自动切换与故障边界

- 各任务只从自己的候选中选取替代节点，并根据自己的探测模板和近期证据判断故障。
- 保留切换前复测、成员与当前选择再次核实、Controller 写入后的回读、持久化意图、同组两分钟冷却及未确认结果阻断重试。
- 自动操作继续与人工选择串行。多个组同时故障时允许独立验证；实际选择由现有 Controller 操作互斥保护串行执行，争用时后续轮次再尝试。
- 修改或关闭某任务的自动切换会取消该任务仍在进行的候选验证；已进入持久化选择阶段的动作按原有锁和审计语义完成。
- 暂停或修改 A 任务只结束 A 任务相应旧方案的 Provider 异常，不会结束 B 任务的异常，也不把暂停描述为网络恢复。
- 数据库写入或维护失败会停止共享调度中的探测和自动切换，并在其他任务概览显示共享存储异常；单个组失效不会触发这一全局停止。

## 验证

新增自动化回归覆盖：慢组与快组共同运行、执行槽位上限、按组暂停和元数据取消、全部任务重启恢复、滚动总预算与比例额度、同时故障时的切换归属、跨组冷却和未确认结果隔离、幂等请求重放边界、共享存储故障、任务历史/事件/序列隔离，以及任务级 HTTP 接口。

测试使用临时 SQLite、确定性模拟源及模拟 Controller。目标路由器在不同组数、候选数和响应时延下的实际覆盖率、CPU、内存与存储开销仍需单独验收。
