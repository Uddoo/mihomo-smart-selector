# 持续监控与长期评分设计提案

状态：P1 与故障自动切换已完成验证并部署；P2/P3 仍为提案。日期：2026-09-08。

P1 实施取舍：每个 Controller 一个当前方案；固定 120 秒基准采样、30 秒当前节点附加采样，共享并发但后台单 worker；界面使用 5 秒鉴权轮询而非 SSE；先保留 7 天原始数据、提供 24 小时评分，不含小时聚合、Provider 相关告警、外部通知和长连接验证。下面仍保留完整后续设计，已实现行为以 [使用说明](../monitoring.md) 为准。

追加功能：用户已授权实现故障自动切换。已加入可选开关、成功率优先候选选择、切换前验证、审计与2分钟冷却；当前行为见使用说明。以下保留初始阶段规划。

## 目标与边界

增加“持续监控”页面，持续观察服务候选节点，提供当前健康状态、24 小时/7 天评分、故障与恢复历史。现有手动扫描用于发现候选和即时复测，新功能负责跨时间积累证据。

采用一次启用、服务端持久运行的模式：首次打开页面显示待启用配置；点击“开始监控”后配置写入 SQLite，Go 后台运行。关闭浏览器继续采样，服务重启后恢复配置，重新打开页面立即显示已有历史。多标签页/多台电脑只订阅同一任务，不重复采样。仅打开页面的 GET 不创建新任务。

若后续确需“仅页面打开期间测试”，可增加有过期租约的会话模式；不作为长期监控默认方式，不能靠浏览器计时器承担后台调度。

第一版不自动切换生产组，不自动修改 OpenClash 配置，不把 HTTP 可达性称为 Codex 长连接稳定性。持续功能由本项目后端实现，不依赖 Codex 定时任务。

## 页面

导航增加“持续监控”，现有扫描保留。

1. 顶部：服务与目标组、运行/暂停/恢复中、当前组选择、最近采样、下次执行、累计观测时长、有效覆盖率。
2. 当前节点卡：健康/疑似异常/不可用/恢复观察/未知；最近失败、连续失败数、最近成功。不能以组当前选择替代已有连接实际路径。
3. 长期榜单：1h/24h/7d，当前状态、长期分、覆盖率、样本量、成功率、估算故障时长、故障次数、P95、最近复测、Provider。即时扫描分与长期分使用不同标题和量程。
4. 详情：时间轴分别显示成功、节点失败、环境异常和缺测；延迟曲线、故障起止区间、切换事件、身份/配置变更。缺测不绘制为连续健康。
5. 故障中心：状态变化生成一条事件，恢复关闭事件；重复失败更新计数，不连续弹窗。
6. 控件：开始/暂停、添加候选、移除候选、立即复测、导出删减后的诊断数据。初期可默认选择“当前节点 + 最近扫描前五名”，去重后最多六个；节点集合保存后不随每轮排名频繁改变。

页面实时更新优先使用带游标的 SSE；断线后恢复订阅并回读快照。现有 HTTP WriteTimeout=30s，实施时需要明确流式响应写超时与心跳策略，不能直接套用普通响应的固定超时。浏览器通知需可选授权，页面关闭时默认只有服务端事件记录，不承诺系统通知。外部通知渠道不在首版内。

## 调度与请求预算

建议初始参数，可配置并显示预计请求量：

| 类型 | 默认周期 | 用途 |
|---|---:|---|
| 所有监控候选 | 120 秒，每节点每目标一次 | 公平的长期评分样本 |
| 当前节点附加检查 | 30 秒；与基准采样到期时合并 | 尽快发现实际使用节点失效 |
| 故障确认/恢复确认 | 失败后约 10 秒再确认；有上限及退避 | 当前状态转换，单独标记，不增加长期评分权重 |
| Controller 心跳 | 30 秒，所有任务共用 | 区分控制器故障与节点探测失败 |
| 环境对照探测 | 平时低频，候选成批失败时触发 | 判断广泛服务异常，不预设唯一根因 |

单目标六节点基准 4320 次/天；当前节点附加检查约 2160 次/天，合计约 6480 次/天，不含心跳、对照和确认。真实流量需要实测，不能仅按请求数量声称零成本。多个 Profile/目标会增加请求量。

默认后台并发上限 2，并且纳入与手动扫描共用的全局探测额度；建议网络探测总预算 12 次/分钟，Controller 元数据读取另行限速。优先保留当前健康检查，手动操作可抢占非关键后台候选。过载时跳过已过期任务并记录缺测，不堆积补跑。跨任务对同一 Controller、节点身份、Profile 版本和采样时隙去重。明确截止时间及取消传播；不同任务启动时间分散，避免整点并发。

失败后退避仍必须保留固定基准采样以比较长期指标；若预算无法满足，降低监控规模并显示实际覆盖率，不暗中改变评分样本频率。

## 健康状态与环境异常

初始状态 unknown。一次失败进入 suspect；在限定时间内两次独立探测失败进入 unavailable；一次成功进入 recovering；之后三次成功、跨至少两个基准时隙才回到 healthy。具体阈值作为初始策略，压测和真实数据校准后再调整。

暂停、Controller 401/不可达、调度漏测、服务停机区间均不得直接归为叶子节点失败。Controller 正常而节点 healthcheck 504 可记录为“经 Controller 观测到节点路径超时”，不能声称已确认服务器宕机。

多个 Provider 同时失败、对照目标也失败时记录疑似环境异常。保留原始结果，分别显示用户可见失败与环境归因；不能因推测“环境问题”删除所有失败并制造高分。无法归因标记 uncertain。

Provider 相关告警示例：同轮同 Provider 监控节点至少三个、其中 80% 失败且另一 Provider 有成功证据时显示“该 Provider 所监控候选疑似共同异常”。显示分母，不外推整个订阅或协议。

服务重启不补造停机期间样本。现有连接表只证明采集时的连接路径，不证明某个历史 WebSocket 的整个生命周期；默认不持续收集全网访问记录。

## 长期评分 v1

评分名称为“长期 HTTPS 健康分”，0–100。WebSocket/业务验证未配置时显著显示“长连接未验证”。

分开提供 1 小时、24 小时和 7 天窗口，不将窗口混为无法解释的单分。默认长期榜看 7 天，数据尚不足时看 24 小时暂定值。

只使用固定两分钟基准时隙，额外确认、手动复测和旧手动扫描作为旁证，不直接混入长期样本；同一时隙只有一个有效结果，不能覆盖失败为重试成功。多目标先按 Profile 固定规则形成时隙结果；目标/期望状态/传输方式不同则分版本，不跨版本混算。

建议初始公式：

S(W) = 70 × A(W) + 20 × C(W) + 10 × L(W)

- A：有效基准时隙中的成功比例；每个时隙等权。单独同时展示有效时隙/计划时隙作为覆盖率。
- C：连续性项。对有效相邻基准时隙中确认的故障段计数，按有效观测小时归一化。初始 C=max(0,1-故障段数/(有效观测小时/6))，即每六小时一次故障已耗尽该项。短窗口波动大，所以 1h 主要展示状态，分数标记短期参考。
- L：成功样本 P95 的归一化，初始 L=max(0,1-P95/1000ms)。没有成功样本则 L=0；全失败不能因延迟缺失获得加分。按 Profile 可配置标尺并版本化。

系数是待验证的产品初值，不是统计保证。需用“快但频繁断线”“慢但稳定”“中断后恢复”“漏测严重”的合成序列和持续试运行数据验证排序。

故障时长根据观测区间估算，展示两分钟采样精度；跨缺测的区间为未知，不制造准确到秒的故障时长。跨统计窗口边界的故障段需裁切，边界不重复生成新故障；长缺测后恢复的首次失败不与缺测前强行拼接。

发布规则：

- 首轮即显示当前健康状态；少于 100 个有效基准样本不显示正式长期分，只显示积累中与原始指标。
- 24h 榜需完整经过 24h 且覆盖率至少 80%；7d 榜需完整经过 7d 且覆盖率至少 80%。未达到时显示暂定分/不足依据并从正式榜分区。
- 连续丢失两个基准时隙则当前状态过期，显示未知，历史分可保留但不能推荐为当前可用。
- 展示覆盖率、有效样本、历史长度和最近采样，不能把数据充足标签描述为数学置信区间。
- 当前可用且数据充足优先；当前不可用单独放在下方，即使历史高分也不推荐；不再使用“已复测一律排前”。

例：某节点先前一分钟拿到高分，之后每小时掉线，不会因新一轮短请求成功清空之前的故障历史。故障恢复只更新当前状态，24h/7d窗口中的失败仍保留。

## 传输与业务证据分层

L1（首版）：现有 Controller delay/Provider healthcheck，只能提供短请求路径可达性与时延。Provider healthcheck 不保证指定 HTTP 状态已经校验，页面明确标注证据来源。

L2（后续）：独立本地探测出口、与生产选择器隔离，执行 HTTPS 状态断言、TLS 握手与到自有测试服务的 60–180 秒 WebSocket 保活。需要预先配置隔离出口；没有条件则显示未配置，不能通过切生产组来测试候选。测试服务的长连接通过，也不等于 OpenAI 业务通过。

L3（后续可选）：用户主动上报失败时间，或经显式配置从客户端提取最小化的业务错误/完成事件。只有能关联故障时实际路由节点、时间与请求结果，才作为该节点的业务旁证。登录凭据不通过浏览器传入，也不默认读取聊天内容。没有授权与完成事件时不自动发送真实模型请求，不声称业务完成率。

三个层级分别展示，不把缺少 L2/L3 当零分，也不将 L1 的高分换名为 WebSocket 稳定分。

## 持久化与身份

复用 SQLite/WAL，新增结构化表而非不断创建整轮 scan JSON：

- monitor_jobs：Controller、目标组、Profile 版本、启用状态、周期、预算、配置 revision。
- monitor_nodes：任务与节点身份关联、加入/移除、已观察配置版本。
- monitor_samples：计划时隙、实际采样时间、类型、结果、延迟、归因、节点身份与算法版本；对去重身份建立唯一键。
- monitor_incidents：状态变化、首次失败/恢复区间、环境与 Provider 相关事件。
- monitor_rollups：小时计数、覆盖/缺测、故障区间摘要和可合并的延迟分布。

节点身份至少包含 Controller + Provider + name + protocol；能从受支持接口取得非敏感出口配置指纹时再加入版本。只有名称不能保证同名节点不换出口；无法取得指纹时界面标注身份连续性限制，订阅更新作注释，不宣称精确检测所有换线。Profile 变化、用户重置身份必须分段；不落盘密码/订阅 URL。

原始样本建议保留 7 天、小时聚合 90 天、事件 90 天；默认容量上限 100 MiB（数据库与 WAL 分项显示，预留超限空间并说明页文件不一定立即收缩），超过时按策略缩短最旧细粒度历史或停止持久采样并告警，不能静默丢记录还更新评分。必须先成功聚合再删除原始样本。

跨日 P95 从直方图/可合并分布或原始样本计算，禁止平均各小时 P95。数据库操作短事务，探测时不持锁；复用单写入连接，关闭前刷新队列，异常重启标记未完成采样为未知。去重写入确保重试不重复计分。监控清理与原有手动扫描清理分开，不高频 VACUUM。

## 实现落点

- 新增 internal/monitor：调度、状态机、去重、分数和事件；从现有 scan.Manager 抽出共享探测调度，不启动互不约束的两套 worker。
- internal/history：增量迁移及监控表读写、聚合和清理；保留旧 scan/switch 审计。
- internal/config：MonitorSettings 与校验，独立 revision。
- internal/api：/api/v1/monitor 下 jobs、overview、nodes、series、incidents、events；遵循现有认证/CIDR，写操作带 revision，GET 无启动副作用。
- web/src：新增 MonitoringPage.vue、监控 API/状态类型、排名与图表组件；App.vue 增加导航。
- cmd/mihomo-smart-selector/main.go：加载持久监控任务，纳入启动恢复与有序停止。

## 交付阶段与验收

P1：后台持续采样、SQLite 原始历史、监控页面、状态/覆盖率、24h暂定分、事件；多页面/服务重启/调度过载不会重复计分或造失败；不自动切换。

P2：7d正式榜、小时聚合与保留上限、Provider 相关异常、故障诊断导出，页面展开分数解释。

P3：隔离长连接探测与可选客户端业务旁证，单独展示验证层级。

自动切换另行设计，需考虑观察期、候选新鲜度、跨 Provider 分散、冷却、切换审计、已有连接与人工锁定，不隐含包含在监控启用动作里。

验收应覆盖：窗口边界、午夜/时钟跳变、全失败、缺测、恢复不抹历史、身份变更、Controller失联、数据库失败、双页面订阅、重启恢复、暂停及停机、与手动扫描争抢预算、真实嵌入页面响应与鉴权。用“节点A先可用后超时、节点B相反”的确定性序列复现本次故障模式。路由器小规模试运行至少24h测量CPU、内存、写入量和缺测率，7d后再评估长期排序效果。
