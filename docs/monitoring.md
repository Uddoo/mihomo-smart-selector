# 持续监控（P1）

持续监控在 Go 服务中运行，开启后不依赖浏览器计时器。它积累节点在不同时刻的 HTTPS 探测证据，不等同于 Codex WebSocket 或真实业务完成验证。

## 开始使用

1. 打开“持续监控”，选择业务 Selector 和已配置的服务模板。
2. 勾选 1–6 个叶子节点。节点数乘模板的探测地址数不能超过 6；默认建议当前叶子节点和最近扫描候选。
3. 点击“开始监控”。关闭页面仍继续；重新打开页面和重启本项目服务都会恢复同一方案。
4. 可开启“故障自动切换”；也可以保持关闭，在工作台扫描后手动选择。开关与监控方案一起持久保存，暂停监控同时暂停自动切换。

每个 Controller 当前支持一个监控方案。暂停、继续不改变方案身份；暂停期间是覆盖率缺口。更换服务、节点列表、Provider/协议身份或探测地址会开始新的观测记录。旧记录保留至清理，P1 页面只展示当前方案，不提供旧方案浏览器。节点增删不会自动由排名驱动，当前选择不在列表时页面会提示。

## 故障自动切换

默认关闭，不会因升级或首次创建监控而自动开启。打开页面里的开关后，由后端持续执行：

1. 目标组当前选择必须是监控列表中的叶子节点，最近90秒内确认连续至少两次失败，状态为不可用；Controller 元数据须在45秒内回读正常。未知、缺测、疑似异常不会触发。
2. 候选必须属于当前监控方案，状态健康，最近4分钟内有成功观测，且至少有一个有效基准样本。按最近24小时基准成功率降序，成功率相同按P95升序，仍相同按名称排序。这里不使用长期综合分，也不要求先积累100个样本；手动扫描的最低成功率门槛不用于此相对择优策略。
3. 对排名最优者执行一次完整、受预算限制的模板复测。失败则检查下一候选；Controller/预算异常则停止本轮；全无可用候选时不改变当前选择。额外验证不覆盖基准样本。
4. 再次核实策略组仍选择预期旧节点、候选身份和成员关系未变化。手动扫描进行中暂不自动切换；要求严格/地区验证的模板因证据不足不自动切换。
5. 先写持久化切换意图，再执行 Controller PUT，并回读确认。选择历史标注“监控自动切换”。未确认或审计失败的操作阻止后续自动切换，需在选择历史核对。
6. 同组最近一次切换（包含手动选择和未确认尝试）后至少冷却2分钟；冷却记录在数据库中，重启不会绕过。故障处理最多每30秒检查一轮，仍共用后台请求预算。

只在当前节点失效时接替，不因另一个节点分数略高而切换；不自动切回恢复后的旧节点。开关切换不清空监控历史。Controller 不提供原子的条件切换，外部客户端仍可能在最后回读与PUT间改变选择；本项目已通过本地串行、前置回读和结果核实缩小竞争窗口。

切换不会批量删除已有连接。已有连接可能继续使用旧出口，新的连接采用新的组选择；不把配置切换成功误报为客户端任务必定恢复。

## 探测与状态

- 基准周期 120 秒，节点在周期内错开执行；当前节点附加检查约每 30 秒。基准探测到期时优先执行，附加检查不会替换基准样本。
- 疑似故障和恢复观察可在约 10 秒后确认，每节点每 30 秒最多一个同类附加检查，且受到总预算约束。
- 单个后台 worker 与手动扫描共享全局探测槽位，后台最多 12 次探测请求/分钟。槽位占满、预算用完、错过执行窗口记录或表现为缺测，不积压补跑。
- 控制器/策略组/Provider 元数据约每 30 秒核实。Controller 读取失败、鉴权失败、节点身份失效记录未知；Controller 可用但节点路径检测失败记录失败。无法判断具体坏在哪一跳。
- 一次失败为“疑似异常”，连续两次失败为“不可用”。恢复先进入“恢复观察”，至少三次成功且跨两分钟时间桶才返回健康。超过四分钟没有观测，当前状态显示未知。
- 状态变化持久记录，连续同状态不会刷屏；最近 100 个事件在页面中展示。一次成功只能证明这次探测成功。

Provider 节点使用 Controller 的 healthcheck 接口，它不保证已经验证模板声明的期望 HTTP 状态。P1 不运行严格正文验证、WebSocket 保活或自动模型请求。

## 24 小时分数与覆盖率

只使用固定周期的基准样本；确认检测、当前节点附加检查、手动复测和之前的手动扫描不进入评分。

`S = 70 × A + 20 × C + 10 × L`

- A：有效基准样本成功比例。
- C：`max(0, 1 - 基准失败段数 / (有效观测小时 / 6))`；相邻失败基准样本合并，缺测中断连续性。它是基准样本的失败段计数，和状态机确认事件数不同。
- L：`max(0, 1 - 成功样本P95 / 1000ms)`；没有成功样本则整项为零，全部失败总分也为零。
- 覆盖率：有效基准样本 / 计划时隙；未知样本和没有记录的时隙都降低覆盖率，不计入节点成功/失败分母。
- 少于 100 个有效样本不显示分数。累计满 24 小时且最近窗口覆盖率至少 80% 才标记“数据充足”；其余为“暂定分”。此标签不是统计置信区间。
- 故障时长由失败基准时隙估算，精度约两分钟，不是精确业务停机时长。

当前健康节点优先；其余状态不当作当前可用推荐。历史高分不会让不可用节点超过健康候选。页面明确显示缺测和数据量，避免成功率 100% 被理解为从未断线。

## 持久化和边界

监控使用同一个 SQLite/WAL 数据库的新表，样本、健康状态和事件在同一事务写入；计划 revision 防止两个页面覆盖彼此的设置，样本时隙唯一键防止重复计分。关闭页面不会改变计划。

原始样本和事件保留 7 天，按小时清理，不在采样循环中 VACUUM。P1 没有小时聚合、90 天归档、7 天正式榜或独立磁盘配额；固定候选上限、频率预算与保留期限制增长。存储写入或维护失败会停止后台采样并显示提示，修复后点击继续监控。存储设置里的扫描/审计清理规则不删除监控记录。

节点身份由 Controller、Provider、名称和协议组成。相同名称/协议下供应商换了出口仍可能无法识别；重复 Provider 节点名不作为监控候选。Provider 或协议身份变化后停止该候选探测，重新保存方案后开始新历史。

更改全局并发数时，若后台仍有探测在运行，保存会返回稍后重试提示；可以先暂停监控。其他设置不会替换正在使用的探测槽位。

## API

所有接口沿用 `/api/v1` 的 CIDR 与 Bearer 鉴权。GET 不创建监控任务。

| 方法与路径 | 功能 |
|---|---|
| GET `/api/v1/monitor` | 当前方案、24h指标、最近60条基准记录/节点、事件 |
| GET `/api/v1/monitor/catalog?group=…&profile_id=…` | 合法叶子候选、当前选择、建议集合；不返回私有探测地址 |
| PUT `/api/v1/monitor/plan` | 创建/修改；包含 revision、enabled、group、profile_id、nodes |
| PUT `/api/v1/monitor/plan`，`{revision, enabled:false}` | 暂停；Controller 不可用时仍可操作 |
| PUT `/api/v1/monitor/plan`，`{revision, enabled:true}` | 恢复相同配置 |
| PUT `/api/v1/monitor/failover`，`{revision, enabled}` | 开关故障自动切换，不重置监控历史 |
| POST `/api/v1/monitor/retest`，`{revision, node_id}` | 排队额外复测；不修改基准评分或策略组 |

浏览器每 5 秒鉴权轮询，无重叠轮询；离开页面取消读取。使用轮询避免当前 HTTP 固定写超时与 EventSource Bearer 认证问题。页面关闭时保留事件，但 P1 不发送浏览器系统通知或外部消息。

后续范围见[设计提案](design/persistent-monitoring-proposal.md)：小时聚合、Provider 相关故障提示、隔离长连接测试、可选业务旁证。首次启用监控不会自动打开故障切换开关；已开启后暂停/继续会保留此偏好。
